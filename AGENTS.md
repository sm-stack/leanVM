# AGENTS.md

## What this is

This repository holds two proving layers on shared foundations (`parallel`, `primitives`, `bench`). They share no proof format, no transcript and no PCS.

- **The leanISA layer**: a minimal virtual machine and recursive SNARK for signature aggregation and blob encoding, its programs written in the zkDSL. Proofs are not zero knowledge. Its hash is Ethereum's Keccak-256. Its public API is the root of the `leanvm` package.
- **The RISC-V layer**: an rv64im virtual machine and the SNARK that proves its execution, its programs Rust guests, with aggregation trees over its proofs and opt-in zero-knowledge leaves. Its hash is BLAKE2s. Users reach it as `leanvm::rv`.

Each layer's rules below apply to that layer only; the shared sections at the end apply to both.

## Layout

The root `Cargo.toml` is workspace-only: libraries in `crates/`, the CLI in `bins/`, the RISC-V guest SDK in `sdk/`, the RISC-V programs' host crates in `programs/*/host`. Within each layer the rows run in dependency order, leaves first:

`crates/leanvm/src/lib.rs` is the only thing a user imports: every other crate is `publish = false`, so a new user-facing item is a re-export there, and `crates/leanvm/tests/api.rs` is its end-to-end use. The leanISA items sit at its root; the RISC-V machine is one re-export, `pub use leanvm_rv as rv;`, so a new RISC-V user-facing item is a re-export at `leanvm_rv`'s root. The workspace's hosts, the CLI and `bench-mobile/` depend on `leanvm_rv` directly.

The CLI is `bins/leanvm` (package `leanvm-cli`, binary `leanvm`), run with `cargo leanvm <subcommand>` (a `.cargo/config.toml` alias for `run --release -p leanvm-cli --`). The leanISA subcommands sit at the top: `aggregate`, `recursion`, `fibonacci`, `hash`. The RISC-V ones sit under `rv`: `fibonacci`, `guest <elf> --advice a,b,...`, `leanxmss`, `leansphincs`, `falcon`, `stateproof`, `shielded`, `leanda`, `aggregate` (an aggregation tree over copies of one leaf proof, or a signer-set tree), and `bench` (the tracked benchmarks). `--log-inv-rate`, `--tracing`, `--repeat` and `--cooldown` are the CLI's global flags, `--leaf-log-inv-rate` and `--zk` are `rv`'s: `cargo leanvm rv leanxmss --n 400 --repeat 3`. The RISC-V sources are `bins/leanvm/src/rv.rs` and `bins/leanvm/src/rv/{aggregate,tracked,workload}.rs`.

`primitives` is one crate for both layers. Its field types `F64`, `F192` and `F192Unreduced` are shared, as are `mul2`, `mul4`, `mul_unreduced4` and `mul_base8`, free functions in `primitives::field`. Keccak is `primitives::hash`, BLAKE2s `primitives::blake2s`. The RISC-V layer's register types (`F192x1`, `F192x4`, `MixedSums8`, and `F192x8Zmm`/`F192x8ZmmSum`, distinct from the leanISA `field::F192x8`) live in `primitives::field::gf2_64x3::{rv_x86_64, rv_aarch64}`, and its bit-matrix fold is `primitives::bit_fold_rv` (the leanISA `bit_fold` is a different API). Benches: `hash_throughput` (Keccak), `blake2s_throughput` (BLAKE2s), `kernels` (the field products, squares and inverses, `mul4`, and the bit transposes, each alone on one thread, as time per call).

## The leanISA layer

### Documents

- `doc/leanvm/`: the LaTeX specification of the ISA and the SNARK. Build with `cd doc/leanvm && latexmk -pdf main.tex` (output in the gitignored `.build/`; if latexmk fails oddly after renaming inputs or editing `refs.bib`, delete `.build` and rerun). Sections are `body/01`..`10` plus annexes `a` (ring switching), `b` (PCS), `c` (Keccak by GKR) and `d` (novel basis and additive NTT); every symbol is defined once in `preamble/macros.tex`. Each section file's `% !TeX root` points at a driver in `drafts/`, so the editor's build key compiles just that section; run `make-drafts.sh` after adding, renaming or renumbering one.
- `doc/lean_xmss/`, `doc/lean_sphincs/`: the specifications of the two signature schemes, implemented in `crates/signatures/src/lean_xmss` and `lean_sphincs`. leanXMSS has full keys only, plus `mock` keys (real over a short range of leaf indices) behind the `mock` feature, for the signers cache and tests. `crates/signatures/tests/signatures/ethlib/` vendors EthLib's leanXMSS and leanSPHINCS test vectors, both from one EthLib commit; refresh them with `ethlib/sync.sh <ethlib-commit>`. `crates/signatures/src/lean_sphincs/known_answer.hex` is a leanSPHINCS key and signature, from a scheme seed, that the crate must reproduce byte for byte.
- `formal/lean_xmss/`, `formal/lean_sphincs/`: Lean 4 (VCVio) proofs of the schemes' 127-bit classical security in the random-oracle model. Their `Scheme.lean` models every hash input's bytes as the crate computes them, so changing any of them in the crate invalidates the proof. `lake exe cache get` once, then `lake build`.
- `crates/lean_compiler/zkDSL.md`: the zkDSL, a Python subset that compiles to the ISA.

The leanISA layer's one hash function is Ethereum's Keccak-256 (FIPS 202 but for the padding's first byte, `hash::PAD_FIRST`), in `primitives::hash`. The VM's `KECCAK` opcode, one permutation of a state held in thirteen memory cells (`keccak::cell_lanes`), is proven by `crates/keccak_gkr`: its crate docs describe the prover, Annex C the protocol.

Guests are zkDSL under `crates/rec_aggregation/guests/`.

### Three verifiers, one protocol

The leanISA verification algorithm is written out three times, and any change to the protocol lands in all three. `verifier::TAG`, the version string the Fiat-Shamir IV hashes (nothing derives it), and every leanISA Fiat-Shamir label stay at `v1` until leanVM ships on Ethereum.

1. **Rust**, `crates/verifier`: the one native verifier, what `EthereumProof::verify` and `cpu::verify` run. It must stay portable by construction: no dependencies, no `unsafe`, no `core::arch`, no `cfg(target_arch)`, no threads. Pinned by `leanvm_core/tests/verifiers/portable_verifier.rs` and every test that verifies.
2. **Python**, `python-verifier/verifier.py` (no dependencies), for readability. Pinned by `leanvm_core/tests/verifiers/python_verifier.rs`.
3. **Recursive**, `crates/rec_aggregation/guests/lean_ethereum.py`: zkDSL, so proving its execution gives a proof of child proofs. Its size and instruction mix are what the recursion benchmark reports first.

The leanISA prover's crates contain no verifier, in tests either: a prover test checks against a reference, and a test that needs a verdict goes through `crates/verifier`.

The Rust verifier walks the protocol once for two entry points: `verify_execution` checks a proof, and `replay_unchecked` returns the same `Summary` checking nothing. Every check sits behind `Transcript::checked`, so a new check goes there, and nothing else may depend on the mode. Reading the proof is not a check: a Merkle path's position and sizes are pinned in both modes, like the stream's length. **`aggregate` does not verify its children**: it only replays them to build the guest's witness, refusing a child it cannot walk as `InvalidChild`, and the guest's in-VM verification catches the rest as `ProofError`. A caller that has not checked a child calls `EthereumProof::verify` on it first.

The guest is self-referential: it verifies proofs of itself, so `unified_guest` compiles it to a fixed point on its own size. One claim, on the stacked bytecode, is not verified in-circuit: each node batches its children's into one, and only the root's is discharged natively, by `EthereumProof::verify`. A child must commit at least `2^MU_MIN` cells for the guest to open it, so `aggregate` sets `Program::min_log_committed`. `DBG_PROF=1` (with `DBG_PROF_DUMP`, `DBG_DISASM`) gives the guest's per-function and per-pc cycle profile.

### Soundness

In the recursion program, the prover sends the verifier advice, called hints. Hints are untrusted witness data: every hinted value must be pinned by a constraint, so a malicious prover cannot prove an invalid witness.

### leanISA conventions

- **`crates/verifier` is still auto-vectorized**: on AVX-512, LLVM turns table lookups into gathers that lose to scalar loads. Check its x86 disassembly after touching a lookup.
- **Fiat-Shamir:** `ProverState::add_scalar` and `Transcript::next_scalar` bind into the transcript as a side effect, and the public statement seeds it at construction. Never re-observe data that rode the stream.
- **Prover and verifiers derive the layout identically** from announced sizes: a change to `placements_of` or the schema lands in the prover and all three verifiers (`crates/verifier`'s `layout.rs` is the native one). `col_kappas` is derived from `col_kappa_sources`; keep it that way.
- **The opening's lane fold binds the committed witness's top variables** (`whir::commit` documents the layout), so every verifier rotates the terminal point left by `INITIAL_FOLDING_FACTOR` before evaluating the basis, while every other read of the opening's point stays in round order.
- **A failed guest `assert` surfaces as a write-once conflict** naming the function and source line. A conflict that `had 0:0:0` can instead be an ordering bug: a cell read before it was written.
- **Guests are single-file**; the compiler skips `from snark_lib import *`, which exists only for editors.
- **One symbol, one meaning, across the leanVM document** (`doc/leanvm/`), defined in `doc/leanvm/preamble/macros.tex` (check a letter is free first; Annex B's "Symbols" table maps its letters to WHIR/Ligerito/BCHKS25). A sumcheck challenge is `\fc`, keeping `\rho` for the rate. A rename in the document is a rename in the Rust prover, `crates/verifier`, `verifier.py` and the guest, which name their variables after it.
- **Doc labels are an API**: the leanISA crates cite `thm:rbr`, `thm:mca-johnson` and sections of `doc/leanvm/main.tex` by label, and `doc/leanvm/body/NN-*.tex` prefixes match section numbers.

### Benchmarking the leanISA layer

```bash
cargo leanvm aggregate --xmss 900 --log-inv-rate 1 --repeat 3
cargo leanvm aggregate --sphincs 530 --log-inv-rate 1 --repeat 3
cargo leanvm recursion --n 2 --xmss-per-leaf 900 --log-inv-rate 2 --repeat 3
cargo leanvm hash --log-n 17 --repeat 3     # the Keccak GKR alone, as keccak_gkr's `hash_batch`
```

`aggregate` takes a count per scheme (both default to zero) and `--blobs`; `recursion` likewise takes `--sphincs-per-leaf` and `--blobs-per-leaf`. Compare schemes and changes by the reported VM cycle counts. Heavy benches: keccak_gkr's `hash_batch`, pcs's `throughput`, primitives' `hash_throughput`. Slow checks are `#[ignore]`d tests, run by name with `-- --ignored --nocapture`: `aggregate_three_levels`, `aggregate_round_trips_through_the_wire`, `print_whir_query_counts`, `encoding_grinding_bits`. `aggregate_two_to_one` is the fast end-to-end check. The leanISA subcommands use the pool's default topology.

CI's `bench.yml` runs base and PR on one runner, in turns, on an x86-64 (`haswell`) and an arm64 (`neoverse-n2`, `+aes,+sha3`) testbed, and `bench-comment.yml` posts what moved as one PR comment.

## The RISC-V layer

An rv64im virtual machine and the SNARK that proves its execution. Proofs are not zero knowledge unless the prover opts in (`Prover::zero_knowledge`, below). Every rv64im instruction is proven, plus custom ones: the BLAKE2s compression (`blake2s rs1, rs2`) and the multiplication in the extension field `E = GF(2^192)` (`extmul`, `extmac`, `extmulk`, `extmack`, each `rd, rs1, rs2` with every register an address). A program is a guest's ELF file (`programs/<name>/guest`, Rust built for `riscv64im-unknown-none-elf`, loaded by `rv::Guest::from_elf`) or a text assembled by hand with `leanvm::rv::asm`; a run is proven on an advice (a region of memory the prover fills), and its statement is the program's digest and the output (`a0..a3` at `exit`); there is no public input. One run is one proof: a run whose witness exceeds one commitment (`pcs_rv::MAX_MU`) is refused up front with `ProveError::TooLong` (`leanvm::rv::ProveError::TooLong`), continuations being unimplemented.

- `doc/leanvm-rv/` is the LaTeX project describing the machine ISA and the snark that proves it. Its root is `doc/leanvm-rv/main.tex`; build it with `cd doc/leanvm-rv && latexmk -pdf main.tex`, which writes to the gitignored `doc/leanvm-rv/.build/`. Sections live in `doc/leanvm-rv/body/`, numbered `01`..`08` plus the lettered annexes `a` (ring switching), `b` (the PCS), `c` (Flock), `d` (novel basis and additive NTT), `e` (recursion) and `f` (zero knowledge), and every symbol is defined once in `doc/leanvm-rv/preamble/macros.tex`. If latexmk fails oddly (a bibtex error, or a missing `main.log`) right after inputs are renamed or `refs.bib` is edited, remove `doc/leanvm-rv/.build` and rerun; it has not reproduced on unchanged inputs. **Drafting one section:** each section file carries a `% !TeX root` comment pointing at its generated driver in `doc/leanvm-rv/drafts/`, so the LaTeX build key (`F5`, or the extension's `cmd+alt+b`) compiles only that section, numbered as in the full document and with cross-references and citations resolved against `.build/main.aux`; in `main.tex` the same key builds everything. Run `doc/leanvm-rv/make-drafts.sh` after adding, renaming or renumbering a section.
- `doc/compact-class-key.md` specifies the compact class key's wire formats and trust boundary; `doc/big-endian.md` the big-endian verification check.
- The RISC-V layer's one hash function is BLAKE2s, in `primitives::blake2s`: scalar, streaming, and a lane-transposed batched form for the PCS Merkle tree. It stays BLAKE2s, not the leanISA layer's Keccak: its trees, transcripts and the recursion machine's HASH rows hash and prove far cheaper under BLAKE2s (a vectorized compression and a flock circuit, against Keccak and a GKR), and these proofs are not meant to be verified on the EVM. A guest-facing Keccak instruction is a separate question, decided with the leaf that needs one. The VM's compression instruction is the generic gate-list circuit in `rv::semantics::hash` (`Class::Hash.circuit()`), proven like every other class; its witness is word arithmetic in `rv::semantics::hash` (exported as `rv::circuits::blake2s_witness`), pinned to the walk of the gate list by a test.

### API

`crates/leanvm_rv` (package `leanvm_rv`, `publish = false`) holds the implementation and the RISC-V API, which users import as `leanvm::rv`. User-facing types are defined in its private modules and re-exported at its root under their public names, never wrapped. The API is `Program` (`from_elf`, `new`, `measure`, `verify`), `Prover { rate }` and its `ProvenRun`, `Proof`, `Output`, and `aggregate` (`rec::tree`: `Tree`, `TreeShape`, `Leaf`, `LeafShape`, `TreeProof`, `CircuitStats`); each operation returns its own error (`ProveError`, `VerifyError`, `DecodeError`, `TreeError`), and both proofs' bytes start with one header (`envelope.rs`: magic, then version). What the crate's integration tests, benches and the program hosts need beyond that (`Program::execute`, `verify_core`, `check_deferred`, `digest`, `session`, a `Proof`'s transcript `.0`, and the machine's and tables' types and constants re-exported at the crate's root) is `#[doc(hidden)] pub`: callable across the workspace, absent from the documented API. The crate's modules are private, so rustc flags whatever nothing reaches.

### Programs and the SDK

`programs/` holds the programs a guest runs, one folder each, and has no `Cargo.toml`. `programs/<name>/guest` is the guest, a standalone package and its own workspace, with its own `Cargo.lock`, toolchain file (a dated nightly with `rust-src`) and `.cargo/config.toml` (target `riscv64im-unknown-none-elf`, `build-std = ["core"]`, `-T../../../sdk/link.ld`, the release profile), so `cargo build --release` in that folder builds it; the fourteen copies of the toolchain file and config are identical, so change them together. **A guest's I/O is its `main` and nowhere else**: `main` reads the advice (`read`, and `read_unchecked` for a library's `repr(C)` word types, whose layout the host writes with `as_words_unchecked`), calls its library's ordinary functions, and `commit`s the public values; the library knows nothing of the VM. `programs/<name>/host`, where a program has one, is its code off the VM, a member of the root workspace: it builds the guest's advice and the output the guest must give (a `leanvm_guest::Run`, the output being `PublicValues` over what `main` commits), exposes the guest's `ELF`, and holds the tests that pin the guest's library to its reference implementation and run the guest on the interpreter; it knows nothing of proving or reports, which are the CLI's (`bins/leanvm/src/rv/workload.rs`). A host depends on its guest's library by path, so the root `Cargo.toml` names that guest in `exclude` (which takes no globs). The runtime every guest links is not a program but the VM's side of the contract with its guests, so it has a top-level folder of its own: `sdk/` (`leanvm_guest`: `_start`, `read`, `read_slice` and `read_unchecked`, which take values from the advice in place with no copy or decoding, `commit`, which streams words into a BLAKE2s whose digest is the run's four output words at exit, through a static block the instruction compresses in place (a word is a store and a pointer bump; the static is reached only by its address, never by a reference), `advice_words!` sizing a guest's advice region, BLAKE2s over the custom instruction as a streaming `Blake2s`, a `Template` rehashed in place (`Template::chain` for a hash chain) and `hash_with` (`hash_prefix_with` for a message ending inside its last word), a one-shot message written into the instruction's block, a panic that is `unimp`), whose `precompile` module is the only place a custom instruction is written (`.insn r`: `blake2s_compress`, public for a guest that wants the bare compression, the crate's own `blake2s_chain` loop under `Template::chain`, and `ext`, under the safe `ext` module) and its `link.ld`, the memory map, which must match `rv::TEXT_BASE`, `rv::ADVICE_BASE` and `rv::RAM_BASE`. It is a root workspace member, built natively there, and what a guest author outside this repository would depend on. `programs/build.sh` builds every guest into one target directory and refreshes the checked-in ELF fixture `programs/<name>/<name>.elf` that the tests, the hosts and the CLI load. **Rerun `programs/build.sh` after touching a guest or the runtime**: nothing rebuilds the fixtures, so CI would keep testing the old ELF and say nothing. The toolchain files pin a dated nightly, so the same sources and lock files build the same code and data; the symbol table differs with the checkout's absolute path, which enters cargo's crate hashes in the symbol names (`.strtab` alone), so compare the loaded sections, not the files, after a rebuild elsewhere, and keep the checked-in fixtures unless a guest changed; moving to a newer nightly is a change of its own, made in all fourteen toolchain files at once with every fixture rebuilt in the same commit, since a new compiler moves the cycle counts. CI does not diff them. Atomics are why the target is `im` and not `imac`: the builtin target has no compare-and-swap, so a dependency needing one does not compile.

**The workload programs** `leanxmss`, `leansphincs`, `leanda`, `falcon`, `stateproof` and `shielded`: each guest is a `no_std` library and its `main`, and each has a host.

- Off the VM, `leanvm_guest` keeps its hashing (`Blake2s`, `Template`, `hash_with`, `keccak`), `Words` and `PublicValues`, in portable Rust. So a host runs its guest's library natively, to sign, encode and compute the output the guest must give.

- Values are `u64` words, never byte arrays. A byte-aligned word costs eight `lbu`. The advice entries are `repr(C)` word structs, read in place.

- Keep a hash's length known at compile time (`&[u64; N]`, `#[inline(always)]`). Each call then folds to its stores and one `blake2s`. A runtime length brings back `memcpy` and `memset` calls, which cost more than the hash.

- **Pick the hashing form by what repeats.** A hash repeated in one shape (a chain step, a tree node, a few-time leaf, an encoding) is a `Template`: the instruction writes only the compression, so the words the next hash shares (the IV, the parameter, the padding) stay in its block and each hash writes only what changed. A message ending inside its last word (leanSPHINCS's encoding, whose counter is 4 bytes) is a `Template` too, its bytes past the end zero and its length given to `digest_prefix`. A one-shot message of words (a tweak hash, a one-time key's leaf over its chain ends, leanSPHINCS's few-time key over its roots) is `hash_with`: its `Stream` writes straight into the block the instruction reads, absorbing a full block only once more of the message follows, and `write_each` takes the pieces of a message produced piece by piece from a closure and puts a block's arrays at fixed places, so no array of them is built first. A hasher that lives across calls stays on `Blake2s`: `Blake2s` copies its message into a fresh block at each compression, which is what keeps a long-lived hasher's state in registers; a hasher owning its block loses that, since once the instruction has its address the compiler neither removes copies of it nor folds what it holds.

- A field narrower than a word, or a slot picked at run time, is `Template::write` at a byte offset: a word index costs a shift to become an address. A tweak's position and index are 32-bit fields, so a hash that changes only those writes two `sw`s. leanXMSS's Merkle path is unrolled this way, its child and sibling placed by the level's bit with no branch.

- A hash chain, each step's digest the next step's value and a counter field its position, is `Template::chain` (both signature schemes' chains): on the VM its loop is written by hand in `precompile.rs`, eight instructions a step with the compression, which is what the compiler's own loop could not reach. A guest calls `Template::chain`, never the loop, so the loop can change under it. Everything else stays Rust, unrolled where a constant index makes a shift or an offset free (leanXMSS's 42 chain ends, its 32 Merkle levels). leanSPHINCS's tree paths go the other way, one loop that is never inlined (`fold`): its tweak's level is the high half of a word, which a loop keeps as a running sum, where an unrolled path builds each level's word as a constant with a shift.

- **A saved instruction pays only where it takes a table under a power of two** at the size proved: every class's table pads to a power of two, so read `rv bench --cycles-only`'s per-table heights, not the total. A rewrite that trades ALU rows for SHIFT or LOAD rows can double another table.

- rv64im has no carry-less multiply, so leanDA's membership check uses the extension-field precompile: one `extmack` per symbol, `sum += L_x * w_x` with `L_x` in `E` and `w_x` in `K` (`leanvm_guest::ext::mul_add_base`). An unrolled loop measured worse: LLVM strength-reduces it into more pointer updates than it saves.

- `falcon` is Falcon-512 verification as the round-3 specification defines it, integer-only (signing, with its floating point, is the host's: `tide-fn-dsa`'s PQClean mode, seeded so the advice never moves). The NTT is three radix-8 passes per transform, eight coefficients in registers for twelve butterflies; a product by a twiddle is Plantard's (two `MUL`s, `ntt::mul_twiddle`), a product of two transforms Montgomery's (three, `mulw` written as such since LLVM splits it into `mul` and `srai`), and no sum is ever reduced: 64-bit registers hold every intermediate the bounds in `ntt.rs` allow. Hash-to-point leaves its samples unreduced and the final Montgomery reduction takes `c` and the product together (`ntt::sub_centered`): a loop subtracting `q`, or a centering written as one, compiles to a `MULHU` division. SHAKE256 is a sponge over the SDK's Keccak-f[1600] (`leanvm_guest::keccak`), XKCP's lane-complemented round, at the instruction floor of rv64im without rotates.

- `stateproof` is an Ethereum L1 state proof as `eth_getProof` (EIP-1186) gives it: the block hash is keccak256 of the header, whose fourth field is the state root; each read walks the state trie to an account at `keccak256(address)`, then its storage trie to a slot at `keccak256(slot)`, a missing key proven absent. keccak256 is the SDK's (`leanvm_guest::keccak`, software, no precompile), absorbing a node's bytes as little-endian lanes; the walk reads only the RLP headers it needs, a hash at any byte offset assembled from two words since a misaligned load traps, and refuses an embedded node, which no trie keyed by 32-byte hashes has. The fixture is real (`host/fixture/mainnet.json`, written by `fetch.py`: one finalized block's header and `eth_getProof` of slot 0 for 32 accounts), so a read costs what it does on mainnet.

- `shielded` is a privacy-pool spend, the statement of soispoke's minimal shielded pool (BLAKE2s edition, https://github.com/soispoke/evm-spend-challenge/blob/main/SPEC.md): two notes in, two out, a depth-20 tree, the nullifier bound to the note's index, values balancing over `u128` with no wraparound, one statement digest out; the signature, the root's freshness and spent nullifiers stay on chain. Every hash is a one-byte tag then fixed-width fields, so each field sits one byte off its word: `message::Tagged` writes a word as `carry | next << 8` straight into the instruction's block, and `hash_prefix_with::<LEN>` takes the exact byte length, the multi-block twin of `Template::digest_prefix`. The host makes spends in the specification's 1,680-byte input format (three shapes: a transfer, a withdrawal, a dummy input) and lays them out as `repr(C)` words; its test pins the guest to a byte-level reference of the statement. The specification's own fixtures are not checked in (its repository has no license); the guest reproduces their digests and refuses their invalid cases with the same rule.

- The KATs in each host pin the first five to the reference implementations (Falcon's to NIST's round-3 vectors, `programs/falcon/host/kat/`; the state proofs to what a mainnet node answered and to `alloy-trie`'s proofs).

### ACT4 conformance

`conformance/act4/` holds the official RISC-V architectural tests ([ACT4](https://github.com/riscv/riscv-arch-test), riscv-arch-test 4.1.0 at `6e8a4512`), their `I` and `M` suites, 64 tests, for an `rv64im` profile with no misaligned access. ACT4 runs each test on the Sail reference model and builds it again with Sail's results inside, so that the ELF file checks itself. The configuration is `test_config.yaml`, `leanvm-rv64im.yaml` (for the unified database, UDB, which defines `MXLEN` through `Sm` and so needs `Zicsr` claimed too: `rvmodel_macros.h` leaves `STANDARD_SM_SUPPORTED` undefined, so no test touches a CSR), `sail.json` (Sail's regions: leanVM's text and RAM), `link.ld` (the code in the text, everything else in RAM, RAM the smallest power of two holding the image) and `rvmodel_macros.h` (a test ends in `exit` with the output zero on a pass, `a0 = 1` and `a1` the caller when the framework halts on a failure). A failing check's handler reads the check back from the text, which leanVM cannot read, so it traps there, and `leanvm_rv/tests/verifiers/act4.rs` reports the check's description, the value computed and Sail's. `generate.sh` builds the Docker image of `Dockerfile` (Ubuntu 24.04 by digest, riscv-gnu-toolchain 2025.08.08 with GCC 15.1, Sail 0.13.1 and mise 2026.9.17 by checksum, the Ruby and Python tools locked by riscv-arch-test itself) and generates `elf/I` and `elf/M` byte for byte: it strips the symbol naming the compiler's temporary object file, which is random, and clears the compressed-instructions flag that ACT4's alignment directives set though nothing is compressed. **The ELF files are not checked in** (`elf/` is ignored), so `act4.rs`'s two tests are `#[ignore]`d: run `conformance/act4/generate.sh` once (Docker), then `cargo test --release -p leanvm_rv --test verifiers -- --ignored act4`. CI (`.github/workflows/riscv.yml`) runs them on every PR, caching the generated files under a hash of every file in `conformance/act4/`, so the image is only built when one of them changes. Left out by design: `Misalign` (a misaligned access traps, and the configuration says so), `Zicsr` (no CSRs), `Zifencei` (no self-modifying code), and `Zmmul`, whose tests are M's multiplication tests again. `act4.rs` runs every test on the interpreter, proves each and checks the proof with the Rust verifier.

### Read-write arrays

The registers, RAM and the advice are read-write, by timestamped offline memory checking (`doc/leanvm-rv` §sec:memchan). What to keep in mind before touching it:

- **A timestamp is an integer**, `2^40 | cycle << 5 | slot` read as the `K` word with those bits (`tables::SEED_CLOCK`, `CLOCK_START`, `LIVE_BIT`). **The clock rides the state tuple**, `(pc, ts)`, with slot zero, and a row's access in slot `k` carries `ts ^ k`, a column plus a constant, which is what lets one row touch the same cell twice (`add a0, a0, a0`). Slots are `rs1` at 0, `rs2` at 1, the RAM access at 2, `rd` at 3, and a row that skips an access leaves its slot unused (a load reads no `rs2`, a store and a hash write no `rd`); a hash row's sixteen block words take slots 2 to 17. Seeds are at cycle 0 (`2^40`), so the run starts at cycle 1: an access must be strictly later than the one before.
- **Each table has a second flock circuit, its clock circuit** (`tables::clock_circuit`, reference `tables::clock_step`): ports the row's clock `ts`, each access's previous timestamp `prev`, and `step`, all virtual columns of the table, packed in a witness of its own (`tables::N_CIRCUITS` is 21: every class circuit, `tables::N_CLASS_CIRCUITS` of them, then every table's clock circuit). An access pulls `(addr, prev, old)` and pushes `(addr, ts ^ k, new)`; the circuit checks `prev`'s bit 40 equals `ts`'s and, on a live row (bit 40 set), `prev < ts ^ k` over 40 bits; `ts`'s five slot bits are empty positions, forced zero, so the order check's `ts | k` is the `ts ^ k` the tuple carries. **Strictness is the soundness**: with `prev = ts ^ k` a read pulls the tuple it pushes and returns anything. The verdict goes to bit 41 of `step`, and the next clock is `ts ^ step`: one cycle on for a live row, `ts` itself otherwise, bit 41 set on a failure. Every timestamp port is 41 bits wide, so no row pulls a clock with bit 41, and the verifier requires the announced final clock to be live at slot zero with nothing above bit 40 (`CpuError::FinalClock`): a failed row leaves its next state unmatched, the exit row's included. A class with no circuit extends its table's clock circuit with ports of its own (`ClassSpec::clock`, a `ClockCircuit`: its `inputs`, `outputs`, gate list `build` and `witness`, built on `tables::Clock::builder`).
- **Padding rows have clock zero**, which lacks the live bit: their clock does not advance, so their state tuples close around a fill block, and their access in slot `k` pulls and pushes timestamp `k`, cancelling itself. The live-bit equality is what keeps them away from the run: a padding row cannot pull a seed, and a live row cannot pull a padding row's tuple. They are written out by `cpu::Program::execute`, not executed, and touch no memory. **The verifier's notion of a padding row is a clock without the live bit and nothing else**, so a prover may close such rows around any cycle of the program's own control flow rather than a fill block; that is inert too, and the fill blocks exist to make the fill exact, not to make it safe. Any new table has to keep this true: every memory tuple's timestamp must be `ts ^ k` or a `prev` its clock circuit checks, nothing else.
- **Two committed columns per array**: what it holds after the run, and each cell's last timestamp. What it holds before is public for the registers (zero) and RAM (`Coord::Sparse`: the image, then zeros, evaluated in time proportional to the image), and a third committed column for the advice (`ADV_INIT`), which is the prover's. RAM and the advice share `SEP_MEM`; they never share an address, every region's base being a multiple of its largest size (`rv::TEXT_BASE`, `rv::ADVICE_BASE`, `rv::RAM_BASE`), so word `z` of a region sits at `base ^ (z << 3)` and the seed block's address is the free `Coord::IntIndex`.
- **A padding row rewrites what it writes**, its `old` column set to its `new` (the register write's `vd_old`, the hash's `out_old`), which is why a row can never update a cell in place: the hash reads `h` and writes `out` in different words, since no chaining value is a fixed point of the compression.
- **A run is capped below `2^35 - 1` cycles** (`tables::MAX_CYCLES`): past that the cycle count would carry into the live bit. The executor refuses a longer run, and one commitment (`pcs_rv::MAX_MU`) holds far fewer rows anyway. Soundness needs no row bound: a run whose clock wrapped could never reach a live final clock.
- `a_stale_read_unbalances_the_bus` is the soundness regression test (a forged run that serves an overwritten register), `a_forged_load_unbalances_the_bus` its RAM counterpart, `a_forged_store_unbalances_the_bus` the same for a store's `rs2` read (both for `ld`/`sd` and `lw`/`sw`), `a_doubleword_moves_its_value_unchanged` the binding of the word `LD` and `SD` move as a column, `a_misaligned_doubleword_names_no_cell` their bus address, `a_read_of_its_own_push_is_out_of_order`, `a_padding_row_cannot_pull_a_seed`, `a_live_row_cannot_pull_a_padding_tuple`, `the_final_clock_cannot_carry_a_failure` and `a_clock_with_slot_bits_cannot_read_its_own_push` (in `tables/clock.rs`) the clock circuit's checks, `a_write_to_x0_unbalances_the_bytecode_read` the zero in `x0` that a base-field operand's high limbs read, `a_forged_bytecode_read_unbalances_the_bus` and `a_wrong_multiplicity_unbalances_the_bus` (in `crates/leanvm_rv/src/cpu/program.rs`) the bytecode lookup's, `a_forged_extension_product_is_refused` and `a_forged_extension_padding_row_is_refused` the extension-field identities' (a forged product whose bus balances, live and padding), `a_forged_extension_operand_unbalances_the_bus`, `a_misaligned_extension_operand_unbalances_the_bus` and `a_base_field_operand_has_no_high_limbs` its limbs' accesses, and `bus::tests::unmatched_leaves` (test-only, taking the producer alongside the push and pull blocks) names the tuples a forged run leaves unmatched, which says more than a failing proof. `leanvm_rv/tests/verifiers/programs.rs` holds the hand-assembled programs checked by the native verifier, `guests.rs` the Rust guests.

### The RISC-V machine

`leanvm_rv::rv` is the machine, `leanvm_rv::tables` and `leanvm_rv::cpu` prove it. What to keep in mind:

- **The program is public, so decoding is free.** `rv::Entry::decode` turns each word into an `Entry` once: an instruction class, a `flags` word selecting what the class's one function does, the three register cells the row touches, the immediate already sign-extended, and the branch or jump target. `LUI`, `AUIPC` and `JAL`'s link fold to constants added to `x0`, `JALR` is the ALU's flags `INDIRECT | ALWAYS`, `ECALL` is a jump to the halt slot, and everything rv64im does not define (reserved shift encodings, `EBREAK`, CSRs) is an illegal entry. The bytecode lookup returns those fields; no table ever decomposes an instruction word. An entry whose class has no table has tag zero, which no row can read.
- **The statement is about the decoded table**, so the rules that make it RISC-V are checked where a table enters (`rv::Entry::is_well_formed` in `Program::new`): two registers below 32 are read, the cell written is in `1..=32`, the successor is `pc + 4`, the flags are ones the class defines, only a branch, a `jal` or the exit has a jump offset (`dt`), a `jal` reads `x0` twice and has `pc + 4` as its immediate, and a field a class's table holds at a constant has that value (a load's `rs2` is `x0`, a store's and a hash's `rd` is `SINK`, a hash's immediate is 0, an `ld`'s or an `sd`'s flags are 0). The proof system itself is sound for any table.
- **`x0` is hardwired by the decoder.** Every entry names two registers read and one cell written. An instruction with fewer reads `x0`; one with no destination, or with `rd = x0`, writes `RegisterFile::SINK` (cell 32), which nothing reads. So cell 0 is never written, and its seed is zero. A class whose `rs2` is always `x0` (LOAD, LD) or whose `rd` is always `SINK` (STORE, SD, HASH) makes no such access at all: its table reads the register number off the entry as a constant (its `ClassSpec::accesses` list no such access), and the interpreter skips that write.
- **Registers are a read-write array of their own**, under their own separator `REG`, so that loads and stores cannot reach them: 64 cells, a public zero seed, committed final values and timestamps, the same clock and clock circuit as memory. A register's number comes straight from the bytecode, so an access needs no address arithmetic.
- **No integer addition happens on the bus.** A load's or a store's address is its circuit's word, with the misalignment bits ORed back in (`rv::WordAccess::bus_address`), so a misaligned or out-of-range access names no seeded cell and the bus does not balance; a doubleword's misalignment bits are all three low ones, so `ld`'s and `sd`'s word is the sum itself (`rv::WordAccess::word_address`). A hash row's block words are at `v1 ^ 8k`, which is `Coord::Sum(Col(v1), Const(8k))`, the XOR being the sum in `K`. The `EXP` lookup of the leanISA days is gone.
- **State is `(pc, ts)`**, `pc` the real byte address. Instruction `z` sits at `TEXT_BASE ^ (z << 2)` and the bytecode block's address coordinate is `Coord::IntIndex { base, shift }`, whose MLE is linear. Everything sits inside one 2 GiB window and below `0x7FFF_F800` for the code models' sake. A computed or misaligned jump target needs no check: the next row's bytecode read finds no entry.
- **A trap is the absence of a proof** (`rv::Trap`): an illegal or unmapped `pc`, a misaligned or unmapped access, an `ecall` that is not `exit`. Those are ISA behavior; the prover's own limits, the cycle cap and a run that would not fit one proof, are `cpu::ProveError::TooLong`. An illegal word follows the text, so a run falling off it traps instead of sliding into the padding blocks or the halt slot.
- **The halt is an exit.** The run ends on the last slot of the padded text, which is never executed. The verifier claims `a7 = 93` and `a0..a3 = output` on the committed final registers at the Boolean points naming them; the output is the transcript's instance and the program's digest is in its session tag, the digest covering the decoded-table commitment root, bytecode size, entry `pc`, RAM and advice sizes, and the length-framed image. The halt slot follows from the bytecode size. Key-only verification authenticates this digest; an application must authorize a key generated from its intended ELF and class. Mixed rows constrain the supplied key and derive its digest and session in-circuit.
- **The precompile is a class like the others** (`Class::Hash`, table `HASH`): `blake2s rs1, rs2` (custom-0 opcode `0x0b`, `funct3 = 1` on the final block, `rd = funct7 = 0`) compresses the 128-byte block at `rs1` (`h` in words 0..4, the result written to 4..8, the message in 8..16, `rv::Hash`), with the counter in `rs2` and the finalization word in the bytecode's flags; a base that is no word address traps, an unaligned one permutes the words deterministically (a guest bug, not a forgery). Its row has no `rd`, `imm` or `out` columns (constants `SINK` and 0 in its bytecode tuple), and eighteen accesses.
- **The extension-field multiplication is a class too** (`Class::Ext`, table `EXT`, `rv::Ext`): custom-1 opcode `0x2b`, `funct7 = 0`, `funct3` bit 0 accumulating into `c` and bit 1 making `b` a base-field word (`Ext::ACCUMULATE`, `Ext::BASE`, the flag word); `rd = x0` is illegal. `a` is at `rs1`, `b` at `rs2` and `c` at the address `rd` HOLDS: the row reads `rd` (`Access::Read(Register::Rd)`, slot 3, written back as found, its value the port `Word::Dest`) and writes no register. Its nine limbs are accesses in slots 4 to 12 (`Access::Limbs`, from `Clock::limb_slot(0)`): `a` and `b` read, `c` read and rewritten, so `c` may alias `a` or `b`. Elements are three packed words, 8-byte aligned. **It is the one class with no circuit**: `y^3 + y + 1` has its coefficients in `GF(2)`, so each new limb is a sum of products of limbs in `K`, and the table proves `c' = accumulate·c + a·b` by three degree-2 identities over its committed limb columns (its relation, `ClassRelation::Identities(ClassTable::extension_product)`), folded into the table sumcheck at the powers of `xi` past the two bus forms'. Its clock circuit (`Ext::clock_circuit`, k_log 12) also takes `v1`, `v2`, `vd` and the flags, splits the flags into two 0-or-1 ports (`Word::FlagBit`, the identities' `accumulate` and the separator's `base`), and computes `p + 8` and `p + 16` for each pointer by incrementers (`Word::LimbAddress`), so a misaligned or out-of-range limb names no cell. A base-field `b`'s two high limbs are reads of `x0`, which nothing writes: the clock circuit gates their addresses to 0, and their separator is `SEP_MEM + base·(SEP_MEM + SEP_REG)` (`Coord::Scaled`), the one bus separator that is not a constant.
- **The interpreter is the reference** (`rv::Machine`), tested against an executor written from the specification on byte-addressed memory that shares no code with it, and against the RISC-V architectural tests' `I` and `M` suites (ACT4, `conformance/act4/`). `cpu::Program::execute` is that interpreter plus the memory argument's bookkeeping.

### Instruction classes and their circuits

Addition with carries, comparisons, shifts, AND/OR, multiplication and division are Boolean relations no degree-2 identity over `K` expresses, so each instruction class is a Boolean circuit proven by flock (`doc/leanvm-rv` Annex C), and a table only does plumbing. The extension-field product is the exception: it is degree 2 over `K`, so its table states it as identities and has its clock circuit alone.

- **One generic table, specialized by a `tables::ClassSpec`**: the state step, the bytecode read, then the accesses `ClassSpec::accesses` lists, in column, bus and slot order, each a `Slotted` access group and the clock slot of its first access: the `rs1` read, the `rs2` read and the `rd` write or read where listed (exactly when the table's circuits take `v2` and give `out`, or read `Word::Dest`, or for `ClassSpec::copies` move the word, which `ClassTable::new` asserts), and the class's RAM accesses (one `Cell` at the circuit's address, read or rewritten, a `Block` of words from `v1` with a run of them rewritten, or the extension-field `Limbs`); the columns, the bus tuples, the interpreter's slots and the trace's previous timestamps all derive from that list. Every successor is linear: a row pushes `pc4`, or for the class with control flow (`ClassSpec::control`, the ALU: branches, `jal`, `jalr`, the exit) `pc4 + jump`, its circuit's output `jump = taken·(dt ^ indirect·(sum ^ pc4))` (bit 0 left out of the indirect part) gating the bytecode's offset bit by bit, and `rd` receives `out`, which a `jalr`'s circuit sets to `pc4`. **A table is settled at the bus point when every tuple it flushes is linear and it has no identities** (`ClassTable::settled_at_bus`, every table with a class circuit today), so its columns but its register numbers are sent at the bus point `zeta[..tau]` and that share comes off the bus totals (`Layout::reduce_tables`): the table sumcheck runs EXT, the bytecode's producer and each settled table's forms on its register numbers alone (`ClassTable::summed_columns`, `summed_form`), and `TableClaims::new` merges the two kinds of claim in table order. **A table's rows are proven by its relations** (`tables::Relation`, `ClassTable::relations`): its class's function, `Relation::Circuit` (a flock circuit over its own packed witness) or `Relation::Identities` (degree-2 forms the table sumcheck folds in), then its clock circuit; the flock batch, the ring-switched witnesses and the matrix claims follow `CircuitId::ALL`, every class circuit in table order then every clock circuit (`the_circuits_are_the_tables_circuit_relations_in_protocol_order`). A new class is a spec, a circuit beside its reference function in `rv::semantics` that its `ClassRelation::Circuit` names (`ClassCircuit::build`), its flag-word type and reference function in `rv::semantics` (`Alu`, `Div`, ...), a no-op word in `cpu::filler`, and its decoding. A class with no circuit (`ClassRelation::Identities`, a function of its table) may sit anywhere in table order, its identities weighted by `cpu::batch` at the powers of `xi` past the bus forms', in table order, and puts the Boolean checks it needs in its clock circuit through `ClassSpec::clock`. The recursion machine's tables have relations too (`rec::Table::relations`): its packed witness, its ports' sources, its height floor and its flock batch derive from them.
- **Every word the circuit reads or writes is a virtual column** of the table, living in the class's packed witness (`Q_BASE + f` for circuit `f = CircuitId::index`, one committed column per circuit, instance `j` being row `j`): `flags` and `imm` from the bytecode tuple, `v1` and `v2` from the register tuples, a load's `address` and `cell`, a hash's block words, `out`, an ALU's `dt`, `pc4` and `jump`. The bus is the whole binding. `CircuitId::instance` asserts that what the circuit computed is what the interpreter did. A hint (`DIV`'s quotient and remainder) is a port in no column, and what a circuit asserts (`Word::Bad`) rides bytecode slot 10 (`tables::BAD_SLOT`), where the program is zero. **`LD` and `SD` (`ClassSpec::copies`) move a doubleword unchanged**, so their circuit is the address adder alone (`rv::Ld`'s, which `rv::Sd` shares, `k_log` 8) and the word moved is a committed column: `LD`'s `cell` is what its `rd` write pushes, `SD`'s `v2` what its RAM access pushes, one column on both tuples; their table has no flags column (the bytecode tuple holds 0). `LOAD` and `STORE` keep the narrower widths and make no gate for the 8-byte one: bit 2 of their bus address is empty, a load shifts only the cell's low half into place and a store only `v2`'s.
- **Circuits are gate lists over word ports** (`flock::circuit`): inputs, outputs, the constant, then products in the order they are made. A port bit with no gate is an empty row, hence zero, which is what makes a one-bit output such as EXT's flag bits a 0 or 1 field element: give such an output a word to itself and never put a free wire on its spare bits. Port layout and product order define the circuit; XOR order is free. `alu_is_its_reference` pins a circuit to its reference function.
- **One batched reduction for all circuits, one opening for all**: one zerocheck and one lincheck over every packed witness under shared challenges (`flock::reduction::{prove, verify}`, `doc/leanvm-rv` §flock:batch), every class circuit in table order then every clock circuit, right after the commitment and before the bus (they read only the commitment, so the prover frees their batches before the bus's peak; the recursion machine's hash rows likewise), each circuit leaving a claim on its own witness. Both sumchecks are front-loaded like the table sumcheck: every circuit takes part from the first round and is done after its own rounds (the zerocheck binding each circuit's lowest variable first, lincheck its top inner coordinate, as for one circuit), and a done circuit adds only to the coefficient the round's claim fixes. Circuit `f`'s zerocheck takes `λ^f` and its lincheck `α^{4f}`; the zerocheck sends every circuit's `v_a, v_b, v_c` and checks their `λ`-combination. Lincheck sends each circuit's 64 slices, then the value of its matrices' form, and checks the batch's final claim against those values and each circuit's closed terms (pin and `C`); each value is left as that circuit's deferred matrix claim, so the verifier's core builds no circuit. A batch of one is how the recursion machine proves its hash rows. The zerocheck prover is a per-circuit state machine (`zerocheck::CircuitProver`) stepped one round at a time, so all twenty-one circuits' folded tables are alive at once. `pcs_rv::stack` takes one ring-switched region per witness, then one for the bytecode's multiplicity column, then one per register word, and ring-switches all their claims as one family under one map challenge; claims whose points are prefixes of one another (the circuits of one block size) share one pass of the Frobenius products (`ring_switch::PrefixGroup`, also the rows' grouping, by wire), each region closing once.
- **A row's register numbers `a1`, `a2`, `ad` are not committed columns**: they are bit fields of a committed register word (`cpu::layout::RegisterWord`, in a register column after every table's span; `Source::Sliced`), five bits per register read and six for the cell written (the sink is 32), packed low first in that order, the fields the class has. Tables of one height share a word: in table order each joins the first word of its height with room, else opens one in its own register column (`RegisterWord::of`), since they share their table-sumcheck point and so one ring-switched claim. The table sumcheck folds every table's numbers, a table the bus point settles keeping only those, so that all words sit at prefixes of its point: read at the bus point instead, they would be a second prefix group the opening and the rows pay for. It sends each number's bits' evaluations in place of its own (`constraints::BitColumns`), the verifier recombines `sum_b x^b s_b`, and each word's claim is its tables' slices in order, then zeros (`doc/leanvm-rv` §sec:regpack). The bytecode lookup still binds the numbers; the opening binds the bits and zeroes the unused ones (`a_forged_register_number_unbalances_the_bus`, `a_packed_register_word_is_its_slices`).
- **Batch floors.** Flock needs eight instances and a zerocheck cube of `2^13` bits for each of a table's circuits (`ClassSpec::n_blocks_log`); padding rows supply them, as honest instances on zero registers.
- **Witness generation is word arithmetic wherever a circuit has a generator, and the generic walk of the gate list, bit by bit, elsewhere**: ALU, LOAD, STORE, LD, SD, SHIFT, MULH and HASH fill by `Fill::Instance` (`ClassCircuit::fill`), MUL by `Fill::Batch8` on AVX2 only, and every clock circuit has one (`ClassSpec::clock_witness`: `Clock::witness`, and for EXT's, whose ports past the clock's split the flags and add 8 and 16 to the pointers, `Ext::clock_witness` on top of `Clock::witness_with`); DIV and MUL off AVX2 walk. Each generator computes the circuit's values natively and writes its rows in the order the circuit makes its products (all but the multipliers' through `rv::circuits::Products`), so a change to a circuit's gate list must change its generator too. Each is pinned to the walk by a test that covers edge words (zero, all ones, the sign bits, every shift amount, every misalignment) and random instances: `semantics::tests::word_witness_is_the_walk` for ALU, the memory classes and SHIFT, and their own for MUL, MULH, HASH and the clock circuits (`clock::tests::the_word_witness_is_the_gate_walk`, every table's, EXT's included). A new generator needs such a test. HASH's generator is unrolled, so every carry run's place is a constant.
- **Circuit sizes are structure, not measurements**: `k_log` (its `ClassCircuit`'s) and `clock_k_log` per class are pinned in its `ClassSpec` and asserted against the built circuits; product counts are in `doc/leanvm-rv` Annex C. A product can be committed straight at an output port's position (`flock::circuit::Builder::and_output`), which saves the copy; the clock circuit's step uses it.

### The recursion machine (`rec`)

A second machine, proven by the same bus, table sumcheck, flock and opening as a RISC-V run, whose rows are a circuit (`doc/leanvm-rv` Annex E). What to keep in mind:

- **Six tables** (`rec::table::Table`): `EMUL` (`a·b + d` in `E`), `EXK` (`a·k + d`, `k` in `K`), `HASH` (one BLAKE2s compression, the RISC-V `HASH` class circuit's packed witness, proven by flock), `SPLIT` (a word and its 64 Boolean bits), `CAST` (four words as a digest, an `E` element, two halves, four words) and `PUB` (the constants and the statement, public, committing nothing). Each table's slot kinds, slot forms, identities and column count are methods of `Table`; its committed columns are filled from the slot forms, so a new table is its kinds, its forms and its identities.
- **Wires are copy cycles** (`rec::bus`: `SlotKey`, `BusBlocks`; `rec::fixed::FixedColumns`, every slot's `next` and the `PUB` constants, the columns a circuit's wiring alone fixes). Slot `g` of row `z` pulls at key `g << 32 | z` and pushes at a public `next`, the key of the next slot of its wire, so the bus balances only if every slot of a wire carries one value. A wire in one slot (a value the prover chooses) and every padding row (`next` its own key) cancel themselves. A table holds at most `2^32` rows (`RecError::TooManyRows`).
- **The rows never depend on values**: the verifier rebuilds the circuit with `rec::transcript::ProofSource::Shape`, zeros in place of the proof. Folding a product by the constant one or zero, or a sum with zero, into no row is structural (constants are the circuit's own wires), and so is folding an `EMUL` or `EXK` row whose input wires repeat an earlier row's into that row (`Builder::emul_key` orders the factors, and a sum's terms), so both keep that true; a constant made from a proof's value would not.
- **A tree circuit's later builds replay its first** (`rec::circuit::Template`, `Builder::recording` and `Builder::replaying`): since the rows never depend on values, the first build at each position of a tree's `Design` (`Design::templates`) records its rows, wiring and folds, and every later build there computes the values alone, checking each row it makes against the template's. A build that leaves its template (`Finished::diverged`) means some row depended on a value: it is logged, counted in `Design::fallbacks` and rebuilt in full, and the tree's tests, honest and forged children alike, assert that count stays zero.
- **The statement is bound by the transcript, not by the bus**: `CircuitKey::prove` and `CircuitKey::verify` (in `rec::proof`) start from the tree's `SessionId` and absorb the statement's limbs as the instance (`fiat_shamir_rv::LengthPrefixed` over them, their count first). The bus checks a `PUB` row at one random point, which leaves a `K`-linear kernel of a word's four limbs (`a_statement_moved_along_the_bus_kernel_is_refused`).
- A circuit whose witness exceeds one commitment is `RecError::TooLong`, on both sides.
- **Zero-knowledge leaves** (`Prover::zero_knowledge`, `cpu/zero_knowledge.rs`): a first-level node verifies them with the very recorder the native verifier uses (`zk::Recorder` over `Rows`), whose record depends on the transcript's shape alone, so the circuit built from a shape is the one built from a proof. A zero-knowledge leaf's core leaves claims of the plain shape (its public evaluations batched by one challenge), which the tree carries as a plain leaf's. The tree's own proofs are not zero knowledge: they hold only the leaves' proofs, which reveal nothing.
- **`rec::verifier::ProofShape::verify_core`** is a RISC-V proof's witness core in rows (plus the zero-knowledge outer proof when applicable), built from the program, the table heights and the rate, and leaves its `DeferredClaims` as wires. A read is a free wire a hash row absorbs, an equality merges two wires, and a check that no equality expresses is a recorded failure (`Builder::fail`), so the rows never branch on a value. Write new verifier logic over `arith::Verifier` where it is protocol shared with the native verifier; anything rows-only needs a test pinning it to the native code.
- The verifier's layout carries a zero final clock (`Layout::announced`), and `Layout::reduce_tables` adds the announced clock's share to the bus's pull total, which is what lets the rows hold the clock as a wire.
- **Aggregation trees** (`rec::tree`, `leanvm::rv::aggregate`, Annex E §E.6 to E.10). The leaves' rate is their `LeafShape`'s, apart from the tree proofs' `TreeShape::rate`: leaves at a lower rate take fewer queries, so fewer first-level rows, and their provers run in parallel while one aggregator proves every tree proof. A first-level node (`Kind::First`) verifies `arity_0` RISC-V proofs of one program in rows, a node (`Kind::Node`) `arity >= 2` tree proofs of either kind; `arity_0 = 1` is single-proof recursion. Every tree proof states the same words (`TreeStatement`, one flat word list whose layout is `StatementLayout`): its kind, a digest of its leaves' outputs, one claim on each dense polynomial (`DensePoly`: the bytecode table, RAM's image, the nodes' fixed polynomial `W_node`) and each flock circuit's two matrices at one row and one column point. A node's rows (`design.rs`) verify each child with `rec::verifier::RecShape`, the recursion machine's verifier (`rec::proof::TableArgument::verify` is the native and the rows' code alike) over `Rows::hinting`, which takes every evaluation of a fixed column as a hint; the hints become claims on `W_node` at the child's kind bit, and only the root's verifier settles them, against the circuits `Tree::new` builds from the shapes alone. Both circuits share their heights, the bounded fixed point of `Tree::converge`. Each node's claims are reduced (`tree::reduce`) by a small proof the node's prover makes natively (`DenseProver`, `MatrixProver`, on the pool) and its rows verify through `arith::Verifier`; the same verifier code runs natively in the tests. A claim whose scale is zero is not reduced: a first-level node carries no claim on `W_node`, and a parent scales the one it carries by the child's kind. Forgery tests hand the rows a forged reduction proof or a fake child circuit (`a_fake_child_circuit_is_refused_at_the_root`); nothing in the production code branches for them.

### Mixed member-list trees

Mixed leaves use the SDK's domain-separated `members` list convention. The execution output commits to an ordered member list; the First circuit derives its VK label and binds that list to a claim group. `LeafClass` pairs program normalization bounds with the accepted proof shape. Circuit kinds select authenticated fixed-polynomial blocks; a VK digest alone does not bind the leaf shape.

`ZkPlacement::Isolated` puts ZK First circuits in dedicated tiers and returns SMALL LeafWraps. `Shared` puts all First circuits in the base tier. The caller pins placement with the class descriptors and tree shape. Compact keys contain dimensions and commitment roots; loaded trees require sealed verification. The wire formats and trust boundary are specified in `doc/compact-class-key.md`.

The `leansphincs-members` guest verifies signature triples and publishes `BLAKE2s(sphmem01 || public key || message)` members. `fibonacci-members` and `preimage-members` use the same list convention for one member. `crates/leanvm_rv/examples/fixtures.rs` generates and verifies conformance artifacts; `scripts/check-big-endian.sh` checks them on a big-endian target.

### One protocol, native and recursive verification

This is the RISC-V layer's verifier rule; the leanISA layer's three verifiers are above. The native verifier (`leanvm_rv::cpu::Program::verify`) and the recursive verifier (`leanvm_rv::rec::verifier`) run the same core over `fiat_shamir_rv::arith`. `Arith` and `Verifier` execute natively over `VerifierState` or build rows over the circuit builder and the in-circuit transcript. The shared core covers GKR, bus decomposition, the table sumcheck, the program claim, flock reductions, and the opening over `pcs_rv::verifier::OpeningVerifier`. `Verifier::scope` names a stage under which the rows report a failed check. `rec::verifier::tests` checks that the rows leave the native `DeferredClaims` value for value and that forged proofs fail at the expected stage.

Verification has two parts: `verify_core` checks the proof and returns claims on polynomials fixed by the program or the VM's circuits (`cpu::DeferredClaims`); `check_deferred` evaluates those claims. Same-program recursive rows consume the witness-core prefix and carry Bytecode/Image claims to the root; they leave the standalone program-opening suffix unused. Mixed first-level rows close the program claim in-circuit and consume the full proof. Native `verify_core` checks the committed-program opening and exact consumption; its returned program claim remains available for same-program root settlement. A caller of `verify_core` must never drop them. `check_deferred` refuses malformed claims with `CpuError::MalformedClaim`, never a panic. The recursion machine reads the very proof the native verifier accepted, with every Merkle opening that verifier authenticated (`rec::transcript::ProofSource::Proof(proof, openings)`): the prover verifies a leaf with `cpu::Program::verify_recording` and a child with `rec::proof::CircuitKey::verify`, both over `pcs_rv::verifier::Recording`, so each hint is decoded and hashed once, natively, and the rows take its full paths (`pcs_rv::merkle::Openings`, flat buffers) as free wires.

Query positions are stratified (`pcs_rv::whir::Stratum::batch`, Annex B's `def:strata`): each binary digit of the query count is a group whose `j`-th query has its top bits fixed to `j`. This keeps the i.i.d. query bound and lets the rows hash the top subtree once and each query's path only below it (`rec::verifier::Rows::authenticate`). Native and recursive verification share the WHIR configuration and its integer level ladder, so no floating point reaches a proof. The floating-point soundness derivation is test-only (`pcs_rv::whir::config::tests`): `the_table_is_the_derivation` pins `WHIR_QUERIES` to it. Changing a constant the derivation reads (the security target, a folding factor, the grinding bits, the size window) fails that test, whose message holds the replacement rows for the Rust table. Moving the size window also changes the table's type: give each rate that many rows first (`&[]` will do) so that `pcs_rv` compiles.

### RISC-V conventions

- **The RISC-V crates' style** (`flock`, `zk`, `fiat_shamir_rv`, `pcs_rv`, `leanvm_rv`, the SDK and the program hosts, which also carry their strict clippy block, all + nursery + a few pedantic, in their own manifests):
  - **A module is one file, `name.rs`, with its tests inline as `#[cfg(test)] mod tests`.** A directory `name/mod.rs` is for a module with several submodules that are each a subsystem of its own, as `crates/flock/src/zerocheck/` holds `lde`, `multilinear`, `padding`, `round1` and `skip_domain`. A folder around one file, a parent with one or two small child files, or tests in a file of their own make no sense: merge them into the parent's file (`flock::lincheck` holds its partial fold and its product sumcheck, `flock::gadgets` its multiplier), the children's module docs becoming sections of the parent's. No folder in these crates holds a lone `mod.rs`; a few modules outside flock still keep small children or their tests in files of their own, and merge into their parent's file module by module. Keep Cargo target entrypoints (`lib.rs`, `main.rs`, standalone integration tests and benchmarks) in their native locations. Update relative includes and file references when moving a module.
  - **Import types, traits and derive macros at the top of their module**, including test modules; use their short names in signatures, fields and bodies: `proof: Proof`, never `proof: transcript::Proof`. Put function-local imports there too, preserving their configuration gates. When two types would share a name, they are two concepts: rename one (`fiat_shamir_rv`'s wire `ProofTranscript` beside the RISC-V `Proof` it carries), never alias it and never qualify it. The one exception is a standard-library name that conflicts with the prelude.
  - **Write explicit paths without a leading `::`, in imports and executable code.** External dependencies start with their crate name (`pcs_rv::verifier::OpeningVerifier`); local module paths start with `crate::` (`crate::pcs::Rate`). Do not import a local module under an external dependency's name: write its full `crate::...` path instead, so dependency paths resolve consistently. Keep imported types, traits and derive macros unqualified at their use sites, as required above.
  - **Use full paths for function calls when the module makes their meaning clearer**, for example `std::array::from_fn(...)` rather than importing `from_fn` and calling it by its short name. The import rule above applies to types, traits and derive macros; it does not require short names for these function calls.
  - **Keep test-only imports and helpers inside test modules**, with the narrowest visibility their callers need. Share fixtures across crates through a module behind a development-only feature. Keep platform gates on production backends and native coverage of guest code. Delete unused helpers and experimental implementations whose only callers test the experiment itself. Library code that only tests and benchmarks reach is promoted into production or deleted, never gated behind `cfg(test)` or a cargo feature: a benchmark measures the code a proof runs.
  - **Errors derive `thiserror::Error`**, with no hand-written `Display`. A variant carries what a reader needs to find the fault (the level, the table, the address). A wrapper that adds nothing is `#[error(transparent)]` with `#[from]`; one that adds context prints `"context: {0}"` and declares no source, so a chain never prints a message twice.
- **Fiat-Shamir** follows spongefish and `draft-irtf-cfrg-fiat-shamir`: a transcript starts from a `SessionId` (derived from a tag naming the protocol and the relation: the program's digest, the tree's circuits) and absorbs the instance (the output, the statement) as its first message. `prover_message` absorbs and writes in one call, so nothing reaches the proof unbound; `public_message` absorbs without sending (never send a value the verifier already holds, and never re-absorb one that was sent); a hint is written and never absorbed, so only data a bound value authenticates may be one (Merkle openings, against a sent root). The proof is the NARG string (exactly the absorbed bytes) then the length-prefixed hints. Every absorbed encoding is fixed-length and a whole number of 64-bit words, which is what `rec::transcript` absorbs; a new message type must keep both. `challenge_pow` squeezes a 32-byte challenge and absorbs the nonce as a message; zero bits is no step at all. The duplex (`Blake2sDuplex`) frames each compression's counter with its role, a block's length and the preceding squeeze count; output nodes are terminal. Native Rust and `rec::transcript` must agree on buffering, cursor resets and the proof-of-work predicate. The exact encoding and the conditional ideal-compression theorem are in `sec:e2e-fiat-shamir`; ordinary mode indifferentiability is not a knowledge, quantum or unconditional whole-protocol guarantee.
- **The stacked opening observes none of its claims.** Its caller binds every claim first: each value a prover message or part of the instance, each point an earlier challenge or public. `clippy.toml` therefore lists `pcs_rv::stack::CommittedStack::open` and `StackCommitment::verify` (and their `_weighted` forms) as `disallowed-methods`: a caller adds `#[expect(clippy::disallowed_methods, reason = "...")]` whose reason says where its claims are bound. The production callers are `leanvm_rv`'s `commitment` wrappers (`Committed::open`, `Commitment::verify`), whose own callers bind; never call the stack's methods from elsewhere to skip them.
- **Prover and verifier derive the layout identically** from announced sizes. Changes to `placements_of` or the schema land on both sides. The framework's blocks, the lookup arrays' producers and the shared columns are described once, by `Framework::ALL`, `Lookup::ALL` and `Shared::ALL` in `cpu/layout.rs`, and every kappa, block, producer and placement derives from them; keep it that way. Each enum's declaration order is that protocol order: `Shared::col()` is the discriminant, and a compile-time check pins `Shared::ALL` to it.
- **The L0 lane fold binds the committed witness's TOP `INITIAL_FOLDING_FACTOR` variables**, because lane `l` of the interleaved commitment is the stack block `q[l·2^(μ-k) ..)`. That makes the witness's zero tail whole lanes, so `whir::BaseCommitment::new` encodes only `StackShape::n_lanes` of them, and the opening's dense weight, its first `k` sumcheck rounds and the stack allocation shrink with it. **A leaf image is still `2^k` words**, the absent lanes contributing their codeword's zeros, but those zeros LEAD it (codeword lane `t` is stack block `n_lanes-1-t`): their whole 64-byte blocks are then one shared chaining value (`blake2s::ChainingValue::zero_prefix`) the committer hashes once rather than per leaf, and only the image's tail rides the proof, so `PrunedMerklePaths` stores `n_lanes` words per L0 row while `Openings` (what authenticating a phase yields) carries the full image the rows hash. The native verifier derives `n_lanes` from the announced layout to read a row. Since `mu = log2_ceil(placed)`, `n_lanes` is in `[2^(k-1)+1, 2^k]` except when the stack is floored at `MIN_MU`, where it can be as low as 1: the encode saving caps near half, the hashing saving is quantized to whole blocks of 8 lanes, and both are ~0 just above a power of two. The cost is that fold challenges arrive in round order while every transparent weight is written in witness coordinates, so the shared opening verifier rotates the terminal point left by `k` before evaluating it (`whir/verify.rs` before `eval_b_at`). Anything else that reads the opening's point (per-level induced weights, the residual) stays in round order.
- **One symbol, one meaning, across the RISC-V document** (`doc/leanvm-rv/`). All notation is defined in `doc/leanvm-rv/preamble/macros.tex`: define a new macro there rather than inline, and check the letter is free first. Annex B's "Symbols" table maps its letters back to WHIR/Ligerito/BCHKS25, so read it before renaming one. A sumcheck round challenge is `\fc` everywhere, which is what keeps `\rho` free for the rate; `r` is the point a claim is made at, not a challenge. **A rename in the document is a rename in the implementations**: the RISC-V prover and verifier name their variables after the document's symbols, so those names move with the document.
- **Its doc labels are an API too.** `crates/pcs_rv` cites `thm:rbr` and `thm:mca-johnson` by name and several RISC-V crates cite `doc/leanvm-rv/main.tex` sections, so renaming a label breaks those pointers with nothing to catch it. `doc/leanvm-rv/body/NN-*.tex` prefixes match section numbers, so inserting a section renumbers the rest.

### Benchmarking the RISC-V layer

Desktop timing cases without an explicit thread count use exactly 16 total pool threads, dispatcher included, through `parallel::init_with_threads`, with no extra efficiency workers. Tracked proof and tree names end in `-16thread` (before a tree's `-first` or `-node`), replacing the old unspecified names rather than aliasing their history. The existing `-1thread`, `-4thread` and `-8thread` cases still select performance workers through `LEANVM_NUM_THREADS`, including efficiency workers where that setting already did. Raw JSON records `threads`, `performance-threads` and `efficiency-threads` for tracked cases; standalone pooled targets record `threads`. The A/B artifacts keep these counts in each run's per-benchmark `topology` metadata, separate from timed metrics. An old base without compatible fixed-16 identifiers and actual 16-thread evidence has no comparable baseline and is shown as new, never relabeled.

The `rv` timing subcommands default to an exact 16-thread pool unless `LEANVM_NUM_THREADS` explicitly requests the existing performance-worker behavior. The standalone pooled targets (`class_batch`, `class_witness`, `pcs_rv`'s `throughput`, `blake2s_throughput`) always initialize exactly 16 threads, regardless of that variable; `kernels` remains inherently serial. `rv bench --cycles-only` keeps its original names and one count row per workload or node kind. Mobile (`bench-mobile/`) continues to use the device's available parallelism.

The benchmarks we care about:

- `cargo leanvm rv fibonacci --n 2000000 --log-inv-rate 1 --repeat 3` (Fibonacci mod 2^64, on registers)
- `cargo leanvm rv guest programs/hash/hash.elf --advice 50000 --repeat 3` (the hash precompile, from a Rust guest)
- `cargo leanvm rv leanxmss --n 400 --repeat 3`, `leansphincs --n 104`, `leanda --blobs 1`, `falcon --n 28`, `stateproof --n 21`, `shielded --n 1035` (the Ethereum workloads and Falcon-512, the most one proof holds)
- `cargo leanvm rv aggregate --program leanxmss --n 400 --leaves 16 --arity0 4 --arity 4 --repeat 3` (an aggregation tree: each kind of node's rows, committed words and times, then the whole tree; the leaves are proven at `--leaf-log-inv-rate`, 2 by default, the tree's own proofs at `--log-inv-rate`)
- `cargo leanvm rv --log-inv-rate 3 aggregate --program leanxmss --n 400 --leaves 4 --arity0 2 --arity 2 --tracing` (the default shape, 2 to 1, with its tree proofs at the rate the mixed trees' fixtures use: each node's `Build circuit` and stages)
- `cargo leanvm rv aggregate --signers --program leanxmss --n 400 --leaves 16 --arity0 4 --arity 4 --max-claims 6401 --max-groups 16 --groups 4 --overlap 25` (a signer-set tree over distinct leaves, each publishing its signer set, `--overlap` percent of each leaf's signers the previous leaf's: the leaves proven untimed, then the tree bottom-up with `Tree::aggregate_leaves` and `Tree::aggregate`, the last node of a level taking fewer proofs, and the root checked by `Tree::verify_claims` against its claim set, each signer set read as a `ClaimSet` through its program's `label_groups`; the union, each circuit's rows and committed words, each kind of node's proving time, the root's verifying time and the proving's heap peak; `--max-claims` and `--max-groups` give the `Capacity`, required since it sets every circuit's heights, and `--declare half` has the root declare half its union)
- `cargo leanvm rv bench --cycles-only --markdown` (every program above, flock aside: RISC-V cycles and committed words, exact, no proof: `cpu::Program::measure`, which CI's `Counts` workflow, `counts.yml`, puts in each run's summary; and two aggregation trees over leanXMSS-400 leaves at `--leaf-log-inv-rate`, 2 to 1 (`cargo leanvm rv aggregate`'s default shape) and 4 to 1 (the tree above), and the signer-set trees of those shapes, sized for their distinct leaves, each kind of node's rows per table and committed words, from its circuits alone: `LeafShape::measured` gives the leaf shape a measured run's proofs announce, so the tree's key needs no proof)
- `BENCH_REPEAT=3 FLOCK_N_LOG=18 cargo bench -p leanvm_rv --bench class_batch` (flock alone, on every class circuit of the VM)
- `cargo bench -p primitives --bench kernels` (the field and bit kernels, one thread, time per call)

The RISC-V `benches/` targets: `leanvm_rv`'s `class_batch` (each class circuit's batch proven alone by flock: the VM's own circuits and witness generators, the commitment, the reduction and the opening; an argument picks the classes, e.g. `-- hash mul`) and `class_witness` (the walk of each class's gate list, one instance at a time against 64), `pcs_rv`'s `throughput` (commit, open, and the commit's NTT alone), primitives' `blake2s_throughput` and `kernels`.

A tree's name says its shape, `Nto1` for N proofs combined into 1 at every node; `-first` is a first-level node (the RISC-V verifier in rows over N leaf proofs) and `-node` a higher node (the recursion verifier in rows over N child proofs).

**Proving**: `bench.yml` runs one job per testbed and benchmark: each case of `proven()` in `bins/leanvm/src/rv/tracked.rs` (at the sizes a 16 GB runner holds: leanXMSS, leanSPHINCS, Falcon, the state proofs and the shielded transfers at a quarter, no leanDA; leanXMSS also on 1, 4 and 8 threads, `leanxmss-100-1thread`, `-4thread` and `-8thread`, each of which the CLI proves in a process of its own with `LEANVM_NUM_THREADS` set to the count `THREADS` gives it, since the pool is sized once per process, and unpinned to cores, since each job has its VM to itself), each of `proven_trees()` (the two aggregation trees above over leanXMSS at a quarter, `aggregate-leanxmss-100-2to1` and `aggregate-leanxmss-100-4to1`: the leaf proven once, then one first-level node and one node over copies of it, the two benchmarks `<case>-first` and `<case>-node`, each node's stages the children of a `Prove` span around it and the node's peak memory including the first-level node's; the signer-set trees of those shapes, `aggregate-signers-leanxmss-100-2to1-16thread` and `aggregate-signers-leanxmss-100-4to1-16thread`, the same way, each node declaring its children's union; both trees also on 1, 4 and 8 threads, `aggregate-leanxmss-100-2to1-1thread`, `-4thread` and `-8thread` and the same for `4to1`, each proven whole, leaf included, in a process of its own like `leanxmss-100-1thread`), and each `benches/` target above with every benchmark it prints (`class_batch` at `FLOCK_N_LOG=18`, `pcs_rv`'s `throughput` at its default size). Each job builds both sides and runs them in turns, base, PR, PR, base, for `ROUNDS` rounds: `cargo leanvm rv bench --only <case>` gives the proving time, the proof's size in bytes (exact: the inputs are seeded and grinding takes the smallest nonce), the time of each of the proof's stages (`stage.<name>`, the `Prove` span's direct children, `--tracing`'s first level, timed by a `tracing` layer that enables spans only), the process's peak resident memory (`peak-memory`, that case's alone since each job proves one), the proving passes' heap as the global allocator counts it (`heap-peak`, the most bytes live at once above those live when a pass began, and `allocations`, its allocations and reallocations, each the largest over the measured passes; host-side setup is outside them), and the verifying time, and a target's `--json` its own measures: `latency` for a whole operation (each class circuit's proving time with the witness excluded, `pcs_rv`'s commit and open), `per-op` in nanoseconds per call for `kernels`, a hashed block of `blake2s_throughput` and one NTT encode. `bench-comment.yml` posts a size that changed and a time that moved the same way in every round with a median ratio at least 1% from one, every result collapsed beneath; it gates nothing. The RISC-V testbeds are self-hosted runners, `x86-64` on `size-attester7870-x64` (an Intel Xeon Gold 6548N, 32 vCPUs, 64 GB) and `arm64` on `size-attester7870-arm64` (an Arm Neoverse-V2, 16 vCPUs, 64 GB), each built for `target-cpu=native` since base and PR build and run on that one machine: x86-64 measures the AVX-512, VPCLMULQDQ and GFNI arms, and arm64 the NEON field kernels, which are chosen at compile time on `aes` and `sha3` (a generic aarch64 target enables neither, so the arm64 job fails early if its build does not enable them or the CPU lacks what the build enables). Each job prints the CPU and its relevant features, and keys its cache on the CPU model so a native build is never reused on another CPU. In a fork's own repository, which has no such runners, and for a PR from a fork, whose code must not run on them, the testbeds fall back to GitHub-hosted runners with a pinned ISA, since a cached native build dies of SIGILL on an older CPU: `ubuntu-latest` built for `target-cpu=haswell`, and `ubuntu-24.04-arm` built for `target-cpu=neoverse-n2` plus `+aes,+sha3`. A benchmark's name is what base and PR are matched by, so renaming one or changing its input shows it as new, as does one the base cannot run (it cannot build the target, or its first base run fails or prints no JSON, and the job carries on with the PR's runs alone).

`bench.yml`'s RISC-V jobs each run `scripts/ab.sh --ci` on their benchmark, and the script owns the whole comparison (which benchmarks are `benches/` targets, the settings they run with, the order of the rounds, the tolerance of a base that cannot run, `ab.json`), so a local run of it makes the comparison CI makes. `counts.yml` keeps its own steps; `scripts/ab.sh counts` is the same comparison. Run from the Actions tab (`workflow_dispatch`), `bench.yml` compares any two refs on the same testbeds (inputs `head`, default the branch it runs on, and `base`, default the head's first parent, passed to `ab.sh --base`) and leaves its artifacts only, since `bench-comment.yml` posts for PRs alone.

CI also records the kernel, page size, transparent huge page settings and available CPU frequency policies; absent or unreadable optional sysfs files are skipped. Its benchmark processes run in systemd user scopes capped at 16 GiB with no swap. After the `leanxmss-100-1thread` job's timed A/B rounds, each runnable side runs `rv leanxmss --n 100 --repeat 1 --tracing` with `LEANVM_NUM_THREADS=1`. The existing benchmark artifact includes `trace-base.log` when the base completed the benchmark and `trace-head.log`, separate from `ab.json`; the traces do not contribute to the A/B samples. Local comparisons retain their portable execution path and do not collect these extra traces.

- `.cargo/config.toml` pins `-C target-cpu=native` for every target but RISC-V, Android and iOS (cross-compiled guests and mobile packages must not inherit the build host's CPU), and `-D warnings` for rustdoc. `rust-version = "1.95"` is workspace-wide. The root `[workspace.lints]` is the leanISA crates' minimal set; the RISC-V crates carry their own strict block.
- Run any test or benchmark touching either VM in `--release`: the zkDSL compiler stack-overflows in debug.
- One test binary per crate, not one per file: new `lean_compiler` integration tests are modules of `tests/suite/main.rs`, new `leanvm_rv` ones of `tests/verifiers/main.rs`.

```bash
cargo testall                     # release workspace tests
cargo clippyall                   # clippy, -D warnings
cargo docall                      # rustdoc, -D warnings
cargo fmt --all                   # max_width = 120
cargo machete --with-metadata     # unused dependencies, dev ones and the guests included
ruff format --line-length 150 python-verifier/verifier.py   # and `ruff check` it
```

```bash
RUSTFLAGS="-C target-feature=+avx512f,+avx512bw,+avx512vl,+avx512vbmi,+vpclmulqdq,+pclmulqdq,+gfni,+avx2,+aes" \
  cargo clippy --release --workspace --all-targets --target x86_64-unknown-linux-gnu -- -D warnings
```

It needs `rustup target add x86_64-unknown-linux-gnu`, and, since jemalloc's build script compiles C for the target, a C compiler for it: `bench` links jemalloc, and the CLI and the `benches/` targets of `primitives`, `pcs`, `pcs_rv` and `leanvm_rv` link `bench`. Without a cross `gcc` (an Apple machine), check the libraries alone, which covers every AVX-512 arm:

```bash

  cargo clippy --release --workspace --exclude leanvm-cli --exclude bench --target x86_64-unknown-linux-gnu -- -D warnings
```

`cargo check` in place of `cargo clippy` (and without `-- -D warnings`) is the faster form of the same check. Use `RUSTFLAGS`, not `CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUSTFLAGS`: cargo lets a set `RUSTFLAGS` (as in CI) beat the target's, and it also replaces the pinned `target-cpu=native`, which no cross target recognizes, where the target-specific variable would be joined with it. ## Benchmarks and tracing

Heavy benches are `benches/` targets (`harness = false`), which `cargo test` never builds; run one with `cargo bench -p <crate> --bench <name>` (each layer's list is above). All of them, and the CLI, time through `bench::Plan` (one warmup pass, then `BENCH_REPEAT`/`--repeat` measured ones, each after a cooldown, reported as mean ± 95% interval). With `-- --json` each prints, in place of its report, Bencher Metric Format JSON, what CI compares.

**Where a proof's time goes is the `tracing` span tree, and only that**: `--tracing` on the CLI, `BENCH_TRACING=1` on the `benches/` targets, `RUST_LOG` to change the level. It records the final measured pass only: `Plan::warm_then_measure` suppresses every other pass (`bench::suppress_tracing`). Each span shows its time, its share of its parent's, its heap peak (the most bytes live while it was open, above those live when the root opened, so a parent's equals that of the child holding it) and the allocations made in it. A new stage worth timing gets an `info_span!` (`stage!` in `leanvm_core`), never an `Instant` behind an env var. To look inside one stage, see Profiling below.

CI compares every PR with its base, never with a history. The base is the merge commit's first parent; a workflow builds and runs both on one runner and saves both as an artifact, and a `workflow_run` workflow on the default branch (`main`, the only branch GitHub runs those from) posts them on the PR as one comment, edited on every run and deleted once nothing changed. Run in turns on one runner, the comparison does not depend on which machine the job landed on, which a history across GitHub's runners does (one runner label spans CPU models of different speeds). The posting workflows never run the PR's code: they take only the PR number from a run's artifact, a fork's included, post nothing unless GitHub's API says that PR's head is the commit the run measured, and check every name and number before it reaches the comment. `.github/scripts/pr_comment.py` (standard-library Python) says what they trust, and its `--dry-run` prints the comment a run's artifacts would give.

### Profiling

The span tree says which stage the time goes to and which stage holds the heap peak, and it stays the only place for stage timings. Two tools look inside a stage, with no code change and no `perf`: gperftools' sampling profiler says which functions, and which of their callers, a stage's time is in; heaptrack says which allocation sites hold the peak heap. Start from the span tree, then profile the stage it points at. The examples profile a RISC-V workload; any CLI subcommand works the same way.

Install them with the package manager (`apt install google-perftools heaptrack valgrind`, the last for `callgrind_annotate`, then `export L=/usr/lib/x86_64-linux-gnu`), or without root by unpacking the packages (Ubuntu 24.04's names; `ldd` on a tool names any library still missing, fetched the same way):

```bash
T=/tmp/prof-tools && mkdir -p $T && (cd $T && apt-get download google-perftools libgoogle-perftools4t64 libunwind8 \
  heaptrack libheaptrack libboost-program-options1.83.0 libboost-filesystem1.83.0 libboost-iostreams1.83.0 valgrind \
  && for d in *.deb; do dpkg -x "$d" root; done)
export PATH=$T/root/usr/bin:$PATH L=$T/root/usr/lib/x86_64-linux-gnu
```

**Function profile**: build with frame pointers, preload `libprofiler` into the CLI, read the profile with `google-pprof`.

```bash
RUSTFLAGS="-C target-cpu=native -C force-frame-pointers=yes" cargo build --release -p leanvm-cli --target-dir target/fp
LD_PRELOAD=$L/libprofiler.so.0 LD_LIBRARY_PATH=$L CPUPROFILE=/tmp/leanvm.prof CPUPROFILE_FREQUENCY=1000 \
  LEANVM_NUM_THREADS=1 target/fp/release/leanvm --cooldown 0 rv leanxmss --n 100
google-pprof --text --no_strip_temp --focus='::prove$' target/fp/release/leanvm /tmp/leanvm.prof | head -40
google-pprof --collapsed --no_strip_temp --focus='::prove$' target/fp/release/leanvm /tmp/leanvm.prof > /tmp/leanvm.folded
google-pprof --callgrind --no_strip_temp --focus='::prove$' target/fp/release/leanvm /tmp/leanvm.prof > /tmp/leanvm.cg
callgrind_annotate --tree=caller /tmp/leanvm.cg
```

- `--text` lists samples per function, self then with callees; `--collapsed` is the input of a flame graph (`inferno-flamegraph`, speedscope); `callgrind_annotate --tree=caller` gives every function's callers, which is how a hot `memcpy` or `memset` gets a name.
- `--focus='::prove$'` keeps the samples under `Program::prove`, dropping the host's own work (leanXMSS's signing, the verification); focus on another symbol to look inside one stage. `--no_strip_temp` keeps what is between `<` and `>`, which in a Rust name is the type of every method.
- `RUSTFLAGS` replaces the `target-cpu=native` of `.cargo/config.toml`, so it is repeated. Without frame pointers most samples get no callers. `--target-dir` keeps the normal build's cache.
- `LEANVM_NUM_THREADS=1`: a pool worker's stack starts at the pool, not at the stage that dispatched to it, so with more threads `--focus` keeps the dispatching thread's samples only.
- `LD_PRELOAD` goes on `leanvm` itself, never on a wrapper: after `taskset`, `flock` or `systemd-run` write `env LD_PRELOAD=... target/fp/release/leanvm ...`. Preloaded into the wrapper, the profiler's timer survives its `exec` and the first `SIGPROF` kills `leanvm` before it has a handler.

**Allocation sites**: `--tracing`'s heap columns say which stage holds the peak and which allocates most, but not which allocation sites inside it; heaptrack says that. It intercepts `malloc`, so it sees nothing of jemalloc. The CLI's `system-alloc` feature wraps the system allocator in `bench::Counting` in jemalloc's place, so heaptrack sees every allocation while `heap-peak`, `allocations` and the span tree's heap columns still count them:

```bash
cargo build --release -p leanvm-cli --features system-alloc --target-dir target/heap
LD_LIBRARY_PATH=$L heaptrack -o /tmp/leanvm-heap target/heap/release/leanvm --cooldown 0 rv leanxmss --n 100
LD_LIBRARY_PATH=$L heaptrack_print -f /tmp/leanvm-heap.zst --print-allocators 0 --print-temporary 0 --peak-limit 10 \
  --sub-peak-limit 2 | c++filt
```

- The report lists the peak's consumers, each allocation site with the bytes it held at the peak and its callers. `heaptrack --analyze /tmp/leanvm-heap.zst` opens the same data in `heaptrack_gui` where it is installed (`heaptrack-gui`), and otherwise prints `heaptrack_print`'s full report (peaks, sites by number of calls, temporary allocations).
- `c++filt` demangles the Rust names heaptrack prints raw.
- The system allocator returns freed pages to the kernel, so this build is much slower (Memory, below) and its timings mean nothing: use it for memory questions only.

## Memory

A proof's buffers are plain `Vec`s on the global allocator, and the libraries impose no allocator. The prover allocates gigabytes of short-lived buffers per proof, so what costs time is the kernel faulting fresh pages in, not the allocator's bookkeeping: an allocator that returns freed pages to the kernel makes every proof fault them in again. The CLI and every proving `benches/` target therefore install jemalloc with dirty pages that never decay (`bench::Jemalloc` and its `malloc_conf` in `crates/bench/src/heap.rs`, one `#[global_allocator]` line in each binary, where the CLI's `system-alloc` feature puts the system allocator instead for heaptrack), so a freed buffer's pages serve the next proof; the price is that the process keeps its peak resident until it exits. On Linux the same configuration asks for transparent huge pages on jemalloc's mappings (`thp:always,metadata_thp:auto`), so a first touch faults a 2 MiB page rather than a 4 KiB one; other targets leave it out, since jemalloc would warn there. A host embedding `leanvm` picks its own allocator, and a retaining one is what makes repeated proofs fast (`leanvm::setup`'s and `leanvm::rv::Prover`'s docs say so). glibc's default is the slow case: it unmaps a large block on free.

Resident memory (`peak-memory`) therefore mixes what the code needs with what jemalloc keeps and how the kernel rounds its mappings, and is the process's maximum, setup included. Each binary wraps its allocator in `bench::Counting` (`crates/bench/src/heap.rs`), which counts the bytes live and the allocations made, over any allocator it wraps: `heap-peak` and the span tree's heap say what the code needs, so a change can lower them and still raise `peak-memory`, and `allocations` measures churn (fresh buffers, regrowth), exact on one thread and varying slightly with the pool's scheduling on many.

A buffer every slot of which the caller writes before reading skips the zero-fill, and large buffers are dropped where their last use ends. The leanISA crates use `primitives::uninit_vec` or `filled_vec` (`T: Plain`, every element written before it is read). The RISC-V crates use `Box::new_uninit_slice` (or a `Vec`'s `spare_capacity_mut`), written through its `MaybeUninit` slots and made a vector by `assume_init` (or `set_len`) only once every slot is written; a kernel typed over `&mut [T]` that writes before it reads takes those slots through `primitives::write_only` (`T: Copy`).

The RISC-V opening's weight is never stored: the first WHIR pass fills it one chunk at a time, and the first fold builds the lane-folded weight in closed form (a point claim's lanes contract to one seed of its eq table, a ring-switched claim's to one GF(2)-linear map of its in-lane eq table), so neither keeps a full-size weight. Weight generation uses bounded aligned windows, capped by the lane block, to amortize map visits. The ARM EOR3 byte-table backend uses longer windows; scalar and x86 byte-sliced backends keep smaller scratch. The first pass initializes its per-worker lane-window scratch directly on the heap, including the zeros needed for padded lanes, rather than constructing a large stack temporary.

## The thread pool (`parallel`)

No rayon. Every parallel site is "N independent items, each writing its own disjoint slice", so the pool is a claim counter, not a work-stealing deque: `NUM_THREADS - 1` workers plus the dispatcher inline, and a dispatch allocates nothing (a reduction allocates its per-worker slots once per call, the slot type being the caller's). Primitives: `for_each{,_chunk}`, `chunks_mut{,2,_zip}`, `ChunkView`, `fill`, `map_collect`, `map_reduce`, `fold_reduce`, `map_reduce_with_state`, `find_first`, `SendPtr`.

- **Nested dispatch panics**, because it would deadlock the dispatch lock.
- **Both core clusters share one queue** (P at `USER_INTERACTIVE`, E at `UTILITY`); guided self-scheduling means a slow core claims fewer batches. Do not add a second pool.
- **One site runs beside the pool**: the leanISA `keccak::while_executing` spawns half the pool's count of plain threads while a program executes, gone before the next dispatch.
- **The default is one worker per logical CPU** (on Linux, per physical core the process may use), holding back one performance worker when efficiency workers exist. The leanISA subcommands use it; the RISC-V timing subcommands and pooled benches pin exactly 16 threads (`parallel::init_with_threads`) unless `LEANVM_NUM_THREADS` is set.

`LEANVM_NUM_THREADS` sets the **performance**-worker count, leaving E-workers in place. `1` = strictly sequential.

Ring-switch claims' weights in `pcs_rv` are built by `ring_switch::DeferredWeight::batch`, which builds each claim's eq tables in turn and then dispatches every composed map of every claim as one task, so one large claim never runs alone; it must not be called inside a parallel dispatch.

## Conventions that bite

- **The prover can be memory-bandwidth bound.** Reduce memory traffic before assuming that more workers or fewer instructions improve throughput. `primitives::stream::Stream` publishes a buffer without the read-for-ownership an ordinary store pays, but ONLY where nothing reads the destination again before it is evicted. Where a consumer follows in the same pass, the fetch it avoids becomes that consumer's miss: fold kernels earn it by building their round message from registers, or by folding into an L1 stage first (the lane rounds' `fold_witness_and_msg`). That fetch is an x86 cost only: on Apple silicon a store-only fill already sustains what a read-only pass does and `STNP` measures identical to `STP`, so `Stream` is a plain copy there and the L1 stage earns its keep for the read locality alone, which is still better than writing through.
- **NEON is the width ceiling on Apple silicon**, so an AVX-512 win that is purely width has no counterpart: the M4 has no SVE, and its SME2 is streaming-mode matrix work with no polynomial multiply. What does port is *shape*. A fused NTT pass wants a butterfly at a time over whole rows, not the register-resident tile the AVX-512 arms use: they transpose anyway and want to pay for it once per pass, while NEON transposes nothing and a tile leaves only its own width of independent work to cover the reduction's dependent PMULL folds, where a row leaves the whole lane count. Measured both directions: the tile costs the extension NTT, and costs the base encode's `Commit` again.
- **A `[F192; N]` in a NEON kernel is a memory object, where on AVX-512 it is the register.** Four tower products are four independent PMULL chains wanting most of the 32 vector registers, so an array of them spills and the spill costs more than batching the products saves; the same array is free on AVX-512, where the quad IS one register. Keep the quad as a tuple or as named values and let arrays exist only inside the batched-product helpers (`primitives::field::mul4`, `flock::zerocheck::multilinear`'s `mul_quad`), on the target that wants them. The symptom is indirect, so suspect the shape rather than the arithmetic: the products measure the same either way, destructuring the results changes nothing, and forcing the helper to inline recovers almost none of it.
- **Rebuild or store is a per-machine choice**, made once in `primitives::REBUILD_OVER_STORE`: x86 rebuilds an intermediate, Apple silicon stores it. A new trade of that kind takes its choice from the same constant.
- **A hot NEON helper that is `#[inline(always)]` stays so.** A `#[target_feature]` function cannot be forced inline, and LLVM then leaves field helpers out of line in hot loops. Split a product's halves by hand rather than with `array::map`. A helper that needs `unsafe` is an `unsafe fn` its callers wrap.
- **On Zen 4, 512-bit cross-lane data movement is half-rate** (every 512-bit shuffle is two 256-bit uops), so packing scalars into vector lanes with `vpermi2q`/`vpermq` and extracting with `vextracti64x4` loses to the scalar moves it replaces. Widening the arithmetic still pays: `mul4` beats the same products issued one at a time. Prefer kernels where both qwords of every 128-bit lane carry a product and nothing crosses lanes.
- **On Zen 5 the carry-less multiplier is the scarce unit, and a CLMUL costs the same at 128, 256 or 512 bits.** Spend it on products only: reduce modulo `x^64 + x^4 + x^3 + x + 1` with shifts and XORs (`gf2_64::reduce`, or its lane-wise twin in the batched kernels), not with the two CLMULs by `0x1B` that NEON prefers, and count CLMUL instructions rather than products when sizing a kernel. The exception is the scalar `F64` product (`gf2_64::x86_64::mul`), whose reduction would cross to integer registers and back: on Zen 4 that loses to the two CLMUL folds, which stay in the vector register. Masked or 512-bit loads of `F192`s passed by value defeat store-to-load forwarding, so the batched kernels pack from scalars.
- **Comments only where necessary**, and concise: uncommented but readable and simple code is better than commented slop.
- **Never put a measurement in a comment, a doc comment, or this file.** Timings, throughputs, percentages and speedup factors go stale the moment the code, the compiler or the host changes, and nothing ever rechecks them, so they end up asserting something false with the authority of a comment. The commit message is where they belong: it is dated, it is immutable, and it says what was true when the change landed. A comment may say which way a result went and why (that a tile lost to whole rows, that one reduction beat another), never by how much.
- **Commit only tests useful against future regressions.** Don't add trivial tests that will always pass. Simpler is better.
- **No em-dashes or en-dashes in prose**, anywhere a human reads it: docs, LaTeX, comments, commit messages. Restructure with a comma, colon, parentheses, or two sentences.
- **Never hard-wrap prose in Markdown or LaTeX.** One paragraph is one line; let the editor wrap it. Artificial line breaks make every later edit a reflow, so diffs show rewrapped lines instead of changed words. Applies to `.md` and `.tex` alike; code blocks, tables and list items keep their own line.
- Grinding chooses the smallest valid nonce, including in parallel. Randomized signature inputs can still make proofs differ between runs.
